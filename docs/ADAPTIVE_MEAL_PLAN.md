# Adaptive meal recommendations

Draft for Pavel's review, 2026-11-12. Scope is product and technical planning. The proposed first release needs no additional provider or API spend. Implementation and provider activation are pending.

## User flow

1. On the first visit to Today or Food each day, show one suggested meal per configured slot. Breakfast, lunch and dinner are the example setup. Use the profile's slot names and order, including any configured snacks. Each suggestion shows the dish, portion in grams, calories, protein, fat and carbs. Show actual intake, remaining targets and projected totals separately.
2. When a diary entry is saved, edited, deleted, undone or received through sync, recalculate actual intake and refresh only the remaining slots. The first food entry marks a slot as logged for planning purposes. Subsequent entries still count. Offer an explicit skip and a way to reopen a slot. An edit to a previous date updates that date's review. It does not change today's totals.
3. If a macro is above target, show the amount above target and rank options by the other remaining goals. If calories are at or above target, show optional lighter meals ranked by calories for a normal serving. Show their projected totals, even when they exceed the target. Use neutral wording and avoid suggesting that the user skip meals, fast or lower tomorrow's target to compensate.
4. In the evening, show a review after the last slot is logged or skipped, or after a proposed default cutoff of 21:00 in the profile's timezone. Include one or two concrete swaps with a reason and a preview for tomorrow. A manual review action also works earlier. If the app is closed at the cutoff, prepare the review on its next open. Label incomplete diary data. The next day's plan uses that day's targets and entries.
5. A suggestion opens a preview that can be adjusted before the user confirms a diary entry. Selecting, refreshing or receiving a recommendation never records food by itself. The weekly menu and shopping list remain independent of the daily suggestions.

Example with synthetic data. A profile has a target of 2,100 kcal, 140 g protein, 70 g fat and 225 g carbs. A logged breakfast of 650 kcal, 35 g protein, 25 g fat and 70 g carbs leaves 1,450 kcal, 105 g protein, 45 g fat and 155 g carbs. Replace the lunch and dinner suggestions using those figures. Adding another breakfast item changes the two remaining suggestions again. The review can show a concrete replacement such as a catalog serving with 160 fewer kcal and 8 g more protein, when the catalog supports those values.

## Calculation and data

- Reuse the diary repositories, `sumEntries`, the active nutrition targets and `settings.mealSlots`. The existing weekly planner in `src/domain/nutrition/planner.ts` provides candidate and portion concepts. Extract reusable catalog assembly from `PlannerPanel.tsx` without changing weekly planning behavior. Use a dedicated daily scoring function that considers all four targets together, respects ordinary portion sizes and reports the closest fit when the catalog cannot match every target.
- Use a small reviewed starter pool plus the profile's own dishes and recipes. Use existing per-100 g and recipe yield math and the nutrition snapshots saved with diary entries. Candidates with missing ingredients or invalid nutrition are ineligible. Apply any explicit exclusions before ranking. If a restriction cannot be verified from ingredients, exclude the candidate and explain the shortage. Use general meal planning within the user's configured goals. Medical diets and target-setting advice are outside scope.
- Keep the signed remainder per nutrient for display. Use a nonnegative scoring budget. Normalize the share of the remaining slots so that a logged breakfast cannot take a share of lunch or dinner. Treat logged and proposed portions separately and show any unmatched remainder.
- Derive suggestions from the current profile, profile date, meal slots, targets, diary snapshot and catalog version. Wait for initial diary loading before proposing meals. Use stable tie-breaking and the existing profile sync. A shared planning timezone is needed for identical dates across devices. Start with a proposed profile preference initialized from the current device and evaluate changes at local midnight. Avoid adding a synced suggestion entity in the first release. Persist a preference only through an explicitly covered settings change.
- Place the main card in Food and a compact entry point on Today. Use existing components, Russian and English translations and the current layout direction. Cover loading, empty catalog, review pending, over-target, skipped slot, and synced updates.

For any provider, use a minimal payload and explain it before activation. Send aggregate targets and totals, allowed candidate identifiers and labels, and only the food entries needed for a requested review. Keep GitHub identity, profile metadata, photos and raw notes out of the payload. Store credentials server-side, keep them out of browser storage and logs, and handle expiry and disconnect. Allow at most one in-flight request per profile and purpose. Debounce batches of diary edits, deduplicate by snapshot and discard stale responses. The local plan still refreshes immediately. Use short timeouts and a local fallback for unavailable providers, refused output and exhausted quota. Reuse existing AI consent patterns where suitable. The current browser-based API key adapters and local call counter are insufficient for server-side OAuth or enforcing cross-device usage limits.

## Direct FitnessMy and Hermes connection

FitnessMy on phone or desktop → Cloudflare Worker and D1 → local bridge on Pavel's PC → Hermes local HTTP API → configured ChatGPT provider. The response comes back through the bridge and Worker and appears in FitnessMy. Telegram is outside this flow.

When the owner enables AI, enqueue a bounded job on the first daily visit, after a committed food change or when an evening review is due. The bridge uses outbound HTTPS to claim jobs and return results. Hermes listens on loopback, with its own local API key. Use a dedicated Hermes profile with only the tools needed for inference. Verify the existing provider can be reused on that profile or use Hermes's supported sign-in. ChatGPT OAuth credentials stay under Hermes management. Confirm access terms and usage limits before real data or automatic jobs. [Hermes API server](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server), [Hermes providers](https://hermes-agent.nousresearch.com/docs/integrations/providers), [Hermes profiles](https://hermes-agent.nousresearch.com/docs/user-guide/profiles).

Pair the bridge with one FitnessMy profile using a revocable credential limited to claiming and completing recommendation jobs. Give the bridge a bounded snapshot with the allowed fields above. Avoid transmitting the complete diary, GitHub session cookies, or reusable provider tokens. Coalesce superseded changes and lease one job at a time. Match each result to the profile, date, snapshot revision and active lease. Expire obsolete requests and prevent repeat completion. Bound poll frequency, retained jobs and provider calls. Verify the expected usage against the existing Cloudflare and provider limits before enabling production.

FitnessMy immediately shows its calculated menu and displays the AI refinement when it arrives. If the PC sleeps or Hermes loses access, FitnessMy keeps the calculated menu and stops waiting after a bounded interval. When the bridge reconnects, process only the newest relevant snapshot. Optional meal edits remain drafts with before and after values. Confirm in FitnessMy through the diary's ownership and revision checks, using an idempotent write.
