# FitnessMy menu variety and interface redesign

Approved scope, 2026-11-12. Pavel selected A, Yellow HUD. See the [interactive design preview](audit/cyberpunk-menu-preview.html) and [visual decisions](../DESIGN.md#cyberpunk-inspired-redesign).

## Daily menu behavior

The current planner ranks candidates for each slot and renders one meal per slot. Hermes can choose a different meal from the same shortlists. The built-in pool has six combinations, three of which use chicken. To deliver three distinct menus, expand the catalog pool and compare complete combinations.

- Show up to three complete alternatives for the same date and the same open meal slots. With breakfast, lunch and dinner configured, each menu starts with all three. Show portion, per-meal nutrition and total proposed nutrition. Keep the actual intake and remaining goals visible above the alternatives.
- Enrich the built-in pool with different protein sources, sides and meal forms using known catalog ingredients and verified portion calculations. Include profile recipes and dishes, retain ingredient exclusions, and verify ingredient references. Target at least three distinct recipe families for each standard slot in an unrestricted new profile.
- Generate a bounded set of full-day combinations. Score fit to the remaining calories and macros, then select alternatives using a pairwise diversity check. For two or more open slots, require at least two differing meals between alternatives where the eligible pool permits. For a single slot, require a different dish in each option. Compare normalized ingredients and recipe family as well as IDs. A portion-only change never qualifies as a different dish. Penalize repeated main ingredients and repeated identical menus across days. Use stable ordering for equal inputs.
- If the catalog cannot provide three valid alternatives, show the options available and explain the shortage. When calories are already at target, prioritize lighter normal portions and show projected totals. Retain the existing nutrition constraints and verified catalog calculations. Changing portions and checking the day totals use the same calculation paths as the current diary.
- Selecting a menu displays it as the preferred plan for the day in that browser. Opening a portion creates a preview. Confirm each diary write explicitly. When a meal is logged, edited, deleted or synced from another device, regenerate only eligible slots. Keep the selected plan visible if it still fits and preserve focus when changed recommendations arrive. Today and Food use the same plan and the next-day preview uses the same diversity rules.
- The local planner supplies the three alternatives immediately. Hermes ranks validated menu IDs and explains its preferred option; the app highlights that option and keeps the numbering and manually selected menu stable. Reject unknown IDs and stale replies, keep local choices available on timeout, and use one grouped request for a changed snapshot.

Keep the existing React, TypeScript, CSS and translation system. The layout and transition work uses CSS without a new animation dependency. Use the existing public `Focus729/FitnessMy` repository and `master` branch. Stage in the current Cloudflare environment and follow `npm run check:release:cloud` and [RELEASE.md](../RELEASE.md). The proposal assumes the existing hosting and Hermes budget.

The first release keeps menu preference and ingredient exclusions per browser and syncs actual diary records through the established profile flow. Model-generated edits to existing records and a shared planning timezone remain tracked in the [adaptive meal plan](ADAPTIVE_MEAL_PLAN.md). The prototype simulates day changes and portion previews with sample data.

The implementation uses a bounded beam for local alternatives, normal catalog portions in lighter mode, and the existing Worker bridge for model ranking. Local Chromium checks covered a real portion write, recalculation, a keyboard-selected menu surviving reload, ingredient exclusions and Russian/English layout at 320, 390, 768 and 1440 px. A two-context cloud fixture used the actual Worker routes and SQLite adapter to verify the phone-to-desktop diary change, a valid Hermes ranking and an invalid response falling back to the local menus. The model response in that fixture was synthetic. The production release record belongs in [PLAN.md](../PLAN.md).
